# Reproduction plan: one branch per measured slide

Status as of 2026-08-31. Slide numbers count the title slide as 1, matching
what revealjs shows with `slide-number: true`. The deck is 18 slides.

Every measured slide's data is regenerated by a numbered script in
`scripts/`, which writes a CSV under `data/`; `slides.qmd` only ever reads
the CSVs. Nothing is transcribed by hand.

## Measurement conventions

- **One node, for microarchitectural metrics.** The same tbb binary
  measured 37.8% memory-bound on jbm035 and 49.7–51.3% on jbm011, so
  memory-bound%/LLC-miss comparisons are only meaningful on one node.
  Scripts 03/08/09/11 pin `--nodelist=jbm033` (`--partition=bigmem` —
  jbm033 is not in `standard`). Script 05 instead requests `bigmem`
  without a nodelist and runs all three builds inside that one job:
  `bigmem` contains only `jbm*` nodes, so any allocation is both one node
  and one hardware family, and it queues far faster than a named node.
  `write_median_table()` refuses to pool runs across nodes either way, and
  requires all three builds present on the node it keeps.
  Wall-clock scaling turned out **not** to need this: `final_scaling.csv`
  was swept across 8 nodes mixing both families (`jst*` = 504 GB,
  `jbm*` = 1008 GB) and the curve is smooth through the family change —
  every step is 93–98% of ideal with no jump at the boundary. Left as
  collected rather than re-run; if that curve is ever re-measured, pinning
  costs nothing and removes the question.
- **Repeats, not single runs.** `05_memory_traffic.py` appends every run to
  `data/memory_traffic_runs.csv` and derives `data/memory_traffic.csv` as
  the per-metric median. Never edit the derived file by hand.
- **Balance is measured per timestep**, then averaged — see
  `common.balance_stats()`. Averaging per-thread across timesteps first
  would flatter a work-stealing scheduler, whose assignment is random each
  timestep, over the static split, which has no such variance.
- **Balance is measured on `worker.range`**, the whole per-thread work
  unit, never on `worker.simulate`. simulate() is only ~50–60% of a
  thread's work; `addBeamToData()` at each patch boundary is most of the
  rest and sits outside the inner timer. A thread doing more of the
  uncounted remainder shows *less* counted time, which reads as imbalance
  exactly when the scheduler is balancing well — that mistake reached a
  draft of slide 9 and inverted its conclusion.
- **The two beam-recompute timesteps are excluded** from balance, leaving
  28 of 30. Where the beam is computed decides whether the timer sees it:
  the static split computes beams inside the dispatch (coverage 100% on
  those timesteps), while TBB and tiled precompute them in a separate
  `parallel_for` outside it (coverage 17% and 2%). On the 28 normal
  timesteps coverage is 95–100% for all three. See
  `common.balance_from_log()`.
- **Builds are comparable**: baseline (`RelWithDebInfo`) and the TBB/tiled
  builds (default `Release`) both end up at `-O3 -march=native` —
  `CMakeLists.txt:110` re-adds `-O3` for any non-Release type.

## Known gaps

1. **Slide 13 bundles two mechanisms.** `3e439717` introduces channel ×
   source tiling *and* `fold_beam_into_simulation`, which removes the
   per-patch buffer round-trip for the stokes-I case entirely (the
   beam-apply remainder goes from 183 s of thread time to 0.5 s). The slide
   says so, but the 1,161→562 s figure cannot be attributed to cache
   locality alone. Separating them needs a build with the fold reverted.
2. **`tiled_final` is not a tiling measurement.** The row is tiling +
   split planes + slab rounding + SIMD at once. Slide 11 no longer shows
   it — it compares static against TBB, both pre-SIMD — but the row is
   still in the CSV; don't reintroduce it as tiling's memory traffic.
   Isolating that needs a build of `3e439717`. The *timing* for tiling
   alone is isolated (slide 13); the memory traffic is not.
3. **Load/store counts are instruction counts**, so a 512-bit load
   replaces eight scalar ones without moving fewer bytes. Harmless on
   slide 11 (neither build is vectorized), fatal in any comparison against
   `tiled_final` — there, use LLC misses, which are cache-line events.
4. **Slide 10's variants are described, not measured here.** The 218 GB
   figure is arithmetic (15.2 MB accumulator × 14,365 patches); the claim
   that they all land within a few percent rests on the two measured
   endpoints (static split, per-source stealing) plus prior work not
   reproduced in this repo.

## Three traps that already produced wrong numbers

**ITT tasks mark one thread, not the loop.** `__itt_task_begin` covers only
the calling thread. TBB emits its own `tbb_parallel_for` task per worker,
but `schaapcommon::StaticFor` has no such hooks, so every baseline worker
landed in `[Outside any task]`: 0.5% of CPU time attributed, against 87%
for the TBB build, and the first three baseline runs reported 29G loads
against a true 4444G. Fixed by `itt::ScopedTask` inside
`PredictSourceRange` plus `predict_range` in `PREDICT_TASKS`;
`parse_task_report()` now refuses a report with under 60% coverage and
names the unattributed tasks.


**The TBB build has three stages, and only the last one performs.** On
`figures/attempt2-tbb-source-parallel` (base `d1005c27`):
`40e31ba7` (naive port) → `018d4d1e` (crash fix, still ~6x slower on normal
timesteps) → `bbeeb2ae` "Centralized beam precompute + persistent
per-thread buffers". The working tree sat at stage 2 for most of a day and
produced a 51% utilization figure, a false 75% regression at 8 threads, and
three memory-traffic runs — all since relabelled `tbb_naive` in
`memory_traffic_runs.csv` and excluded from the median.
**Before trusting any `tbb` number, run
`git diff bbeeb2ae -- steps/OnePredict.cc`**; if `PrecomputeBeamValues` is
missing, it's the wrong build.

**A slide compared a binary against itself.** The removed "CPU usage over
time" slide read `r_timeline_{baseline,tbb}_20260826_1624*`, and VTune's own
recorded argv shows both ran `src/DP3/build/DP3 ... useoriginalpredict=true`
— `presentation_data/baseline_analysis/build/DP3` appears in neither. The
two curves were one configuration measured twice; `boundaries_*.env` agree
(BEAM_END 64.0 vs 65.0). `plotting.cpu_utilization_timeline()` is kept but
unused, with that recorded in its docstring. Any A/B collection must assert
the two binaries differ.

## Why the TBB build needs attention

`steps/OnePredict.cc` is supposed to stay the pristine `StaticFor` baseline
on `rebase-onto-upstream` — it's what slides 4–6 compare against. The TBB
work behind slides 8–9 was written directly into that same file, on that
same branch, uncommitted, and now also carries the `worker.range` timer.
Two consequences:

1. As long as it stays uncommitted, a fresh clone of `rebase-onto-upstream`
   does not reproduce the slide 8/9 numbers.
2. If it were committed as-is there, `OnePredict.cc` would stop being the
   `StaticFor` baseline, breaking slides 4–6 instead.

`figures/attempt2-tbb-fixed`, or extend `figures/attempt2-tbb-source-parallel`

`presentation_data/baseline_analysis/worktree/steps/OnePredict.cc` and in
`steps/OnePredictNew.cc`; all three need it or the balance rows aren't
comparable.
